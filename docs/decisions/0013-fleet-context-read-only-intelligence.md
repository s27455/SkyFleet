# 0013 — Fleet context for the AI gateway (Feature 025)

**Status:** Accepted, implemented and finalized (2026-11-15). Nothing calls it yet: there is no endpoint, no UI, no agent and no model tool, and no paid Anthropic request was made for this feature (the tests use fake transports only).

## Decisions

- **A read-only snapshot of the PRESENT, in one transaction.** `app/fleet_context/snapshot.py` reads everything inside a single PostgreSQL `REPEATABLE READ`, `READ ONLY` transaction with `SET LOCAL statement_timeout = 2000`. Every query sees one committed instant, so counts and rows cannot contradict each other. The database itself refuses any write (`ReadOnlySqlTransaction`), the session refuses to flush, and the transaction is always rolled back, never committed. A read-only repeatable-read transaction takes no row locks, never blocks the simulation worker and cannot fail with a serialization error (verified on PostgreSQL with open writers in both directions). A snapshot takes about 30 ms on the development data.
- **Honest limit of consistency.** The worker commits many small transactions (one per flight, per charging step). A snapshot never shows half of one, but different entities may differ by up to one worker tick (about 1 s). `captured_at` is the application clock at the start of the call.
- **Reuse authoritative rules, never re-derive them.** Docking and Hub occupancy come from `missions.presence`, dispatch eligibility from `dispatch.service.available_drones_by_hub` (the dispatcher's own rule: `IDLE`, battery exactly 100, no active mission, docked), active missions from `dispatch.service.active_claims`, the emergency position test from `simulation.recovery.POSITION_TOLERANCE_DEG`, the helicopter and rain warning from `lpr.active_scenario` and `weather.get_status`, worker liveness from the heartbeat. An architecture test pins the exact names the package may import (only reading code) and forbids every write, lock and raw SQL except the timeout.
- **Status names alone are not trusted.** An order interrupted by a drone failure keeps `OUT_FOR_DELIVERY` forever, so "in delivery" requires an active mission and the rest is reported as `interrupted` (history). An emergency flight is an active incident only while its drone is still grounded (`MAINTENANCE` where the flight stopped) or landing; once the drone is back in service it is a `recovered_alert` (listed only while unacknowledged); acknowledged and recovered emergencies are history and are not read at all. Events, which only say that something happened once, are not used.
- **Present versus history, by construction.** `summary.orders_open` and `active_incidents` are the present. `orders_history` (60-minute window and all-time counters), `recovered_alerts` and the all-time counters are history and are named so. The LPR helicopter and the rain warning are `operational_warnings`, never drone emergencies and never counted as incidents.
- **Bounded and honest about size.** Caps: 40 drones, 12 hubs, 10 incidents, 10 recovered alerts. The roster is ordered in three tiers, each by drone id: flagged drones (by flag urgency), then other drones in flight or holding an active mission, then all the rest. The byte budget is computed from the real question: `ai_max_input_bytes` minus the system prompt, the wrapper and the question's own bytes. When the text is too large it is reduced one entry at a time from the least important end (routine drones, recovered alerts, hubs, flagged drones, incidents); the summary, the simulation block, the limitations and the warnings are never dropped. Every removal is recorded in `omitted`, as a `*_OMITTED:n` limitation, `truncated` true and `data_status` degraded; if it still does not fit the request is refused. The gateway re-validates the complete request unchanged.
- **Uncertainty is part of the data.** `data_status` is `complete` only with no limitation: a fresh worker, nothing omitted, no invariant violated (Hub over capacity, `IN_FLIGHT` drones differing from active flights, unknown status, sanitized text).
- **Fail closed.** If a trustworthy snapshot cannot be built (any error, a timeout, a broken schema) `ask_fleet_question` raises `FleetContextUnavailableError` before the gateway is called: no budget is reserved, no ledger row is written and the provider is never contacted. An invalid question or a disabled AI is refused before any database read.
- **Data stays data.** No coordinates, order addresses, event text or mode summaries are included. The only database text is Hub names and ids, cut to an allow-list (letters, digits, a little punctuation, at most 40 characters) and reported with a `TEXT_SANITIZED` limitation when changed. The fixed system prompt (extended from 267 to about 1.4 KB in `app/ai/request.py`; no new gateway parameter) states the behavior contract and that everything after `Fleet context:` is data; a prompt is not a security boundary, the backend limits and the absence of tools are.
- **Feature 024 is untouched.** `AiGateway.ask(question, context)` and every control in it (readiness, the 16 KiB check on the whole request, the hourly quota, the interval, one request in flight, the durable reservation, the USD 4 ceiling, no retry, no tools) apply as before. The only edit outside the new package is the system prompt text and the boundary test, which now permits `app/fleet_context` (and only it) to import `app.ai`.

## Consequences

- A longer system prompt raises every request's reservation by about 1.1 KB of input (under USD 0.0001); the absolute worst case stays USD 0.0019408.
- Counts over `orders` scan the table each time; at the current size that is milliseconds and the 2 s timeout fails closed if it ever grows too large. The emergency query scans the emergency flights; both are candidates for an index if the tables grow by orders of magnitude (no migration was made).
- Docking is inferred from position (the existing 50 m rule), not hardware-confirmed, and coordinates are not provided, so the model cannot answer "where exactly" questions. Adding coordinates or events later is a deliberate schema version change.
- Measured cost: about 33 ms on the development data and about 0.5 s with 1,000,000 orders, missions and flights; roughly linear, so the 2 s timeout is far away. If the tables ever grow by orders of magnitude, an index on `orders.status` and on the emergency flights is the first remedy.
- Roster priority under truncation: flagged drones first, then drones in flight or on an active mission, then the rest, each by id, so a cut removes idle and charging drones first, then active ones, and flagged ones last. Remaining limitation: under severe truncation a drone named in the question can still be omitted (the counts cover every drone and the omission is always flagged, but the model cannot describe it); pinning the drone ids that the question names is left to Feature 026.
- Every database string, enums included, goes through the text cleaner (defense in depth: the CHECK constraints already refuse hostile enum values).
- Feature 026 (the first caller, with authentication and an endpoint) must call `ask_fleet_question`, never the gateway with a hand-made context, and must show `data_status`, `captured_at` and the truncation indicators to the operator.

## How Feature 026 must consume it

- Call `ask_fleet_question`, never `AiGateway.ask` with a hand-made context: it is the only path that builds the snapshot, fits it to the budget and fails closed. Build the gateway and the call from the same `Settings`.
- Authentication comes first. The API has none, so nothing may expose this before it exists.
- Show the operator `captured_at`, `data_status` and every truncation indicator (`truncated`, `omitted`, the limitations) next to the answer; never present a degraded or truncated answer as complete or live.
- Reject or neutralise the words `Fleet context:` and `Question:` in the operator's question, so it cannot pose as a second snapshot.
- Pin the drone ids that the question names, so a drone the operator asks about is not the one that truncation cuts (the remaining limitation of the roster priority).
- Keep the model tool-free and read-only: no tool, no database access, no write action, and every state change stays an operator action validated by the backend.
- Treat any new field as a schema change: new text from the database must go through the text cleaner, and coordinates or event text are a deliberate `schema_version` bump.
- The first real request that carries a fleet context needs the owner's explicit approval: the real token count validates the reservation bound (the gateway halts itself if it were exceeded), and the Console spend limit stays the real provider cap.
